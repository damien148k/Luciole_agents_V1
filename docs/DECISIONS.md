# Décisions techniques

Une ligne par choix : ce qu'on a décidé, pourquoi, quand. On ne rediscute pas un choix noté sans nouvelle mesure ; si on change d'avis, on ajoute une ligne, on ne réécrit pas l'ancienne.

| Date | Décision | Raison |
|---|---|---|
| 2026-10-18 | Nouveau dépôt, pas une évolution de V5 | V5 porte trois générations de commentaires (V3/V4/V5), un README faux et des défauts structurels (voir `cadrage/analyse-v5.md`) |
| 2026-10-18 | Le cas d'usage est l'objet central (`configs/profiles/<cas>/`) ; le RAG est un outil parmi d'autres | Deux cas d'usage connus (MRAe, commerciaux) ne partagent ni les documents, ni les métadonnées, ni la forme de la boucle |
| 2026-10-18 | Les boucles sont des machines à états en code, décrites en YAML, aux règles déterministes | Post-mortem Belacom : un LLM qui pilote le flux de contrôle a systématiquement fait moins bien qu'un pipeline à étapes séparées |
| 2026-10-18 | Python 3.12 et `uv` avec `uv.lock` | Reproductibilité hors ligne ; casse du 7 septembre 2026 sur V5 quand pip a remplacé torch |
| 2026-10-18 | Profils matériels (`configs/hardware/`) et images Docker `amd64` + `arm64` | Trois machines cibles dont le GX10 en ARM64 |
| 2026-10-18 | Chunking en tokens du modèle d'embedding, parent-enfant | V5 comptait en caractères (1024 caractères ≈ 250 tokens, loin des 512 à 1024 tokens de la spec) |
| 2026-10-18 | `document_id` = hash du chemin relatif et du contenu | V5 utilisait le nom de fichier seul : collisions entre dossiers |
| 2026-10-18 | Qdrant ≥ 1.12 avec vecteurs nommés dès le départ ; OpenSearch gardé pour BM25 | Permet multi-dense puis sparse sans changer de schéma ; BM25 reste la base de comparaison |
| 2026-10-18 | Magasin structuré local (SQLite ou DuckDB) pour les métadonnées | Le cas commerciaux filtre et agrège sur des dizaines de dossiers avant de lire |
| 2026-10-18 | Parser PDF : seuil « page vectorielle complexe » à 5000 tracés, en-têtes/pieds cherchés dans les bandes haute et basse (12 % de la page, ≥ 3 pages), coordonnées dans le repère de la page affichée | Mesuré sur 202 pages d'études d'impact publiques : tableaux ≤ 2000 tracés rendus en < 3 s, cartes ≥ 7000 ; doubles pages A3 tournées de 90° (voir JOURNAL, PR 1d) |
| 2026-10-18 | Un modèle documentaire unique à nœuds (`DocumentNode` : type, page, chemin de section, parent, boîte, méthode, confiance) pour tous les formats ; texte et Markdown sont des projections | Le chunking, les citations et les filtres de l'étape 2 travaillent sur une seule structure, quel que soit le format d'origine |
| 2026-10-18 | OCR derrière un contrat `OcrEngine` (lignes + boîtes + confiances) ; EasyOCR en extra optionnel `ocr`, jamais installé en CI ; un moteur factice dans les tests | Les tests unitaires restent rapides et hors ligne ; le moteur réel se choisit par profil matériel à l'étape 3 |
| 2026-10-18 | Une seule PR à la fois, toujours sur `main` ; plus de PR empilées | Les PR #3 à #5, empilées, ont été fusionnées dans leurs branches intermédiaires et non dans `main` (GitHub ne rebascule la cible que si la branche de base est supprimée) ; il a fallu la PR #6 de rattrapage |
| 2026-10-18 | Magasin structuré : SQLite (bibliothèque standard, JSON1), un fichier par cas d'usage, noms de champs vérifiés contre le profil et valeurs passées en paramètres | Aucune dépendance de plus, fonctionne pareil sur Windows, amd64 et ARM64 ; DuckDB reste possible si les agrégats deviennent lourds (nouvelle mesure requise) |
| 2026-10-18 | Dossier = sous-répertoire de la racine d'ingestion ; `document_id` = sha256(chemin relatif normalisé + hash du contenu), 32 caractères ; une fiche par chemin, remplacée si le contenu change | Deux fichiers de même nom coexistent ; une modification n'empile pas de doublon ; même identifiant sous Windows et Linux |
| 2026-10-18 | Priorité des métadonnées de document : front matter > motifs du nom de fichier (profil) > extracteur (LLM, étape 4) seulement pour les champs encore vides ; dossier : `dossier.yaml` > valeurs des documents, le plus récent selon `document_order` l'emportant (avec avertissement) | Une valeur écrite par un humain prime sur une valeur devinée ; « perdu » à la dernière réunion doit primer sur « en cours » des précédentes |
| 2026-10-18 | Une valeur de métadonnée invalide n'est jamais corrigée en silence : elle est refusée et signalée (erreur, ou avertissement si une autre source a comblé le champ) ; un document incomplet est gardé et signalé, pas écarté | Le cas commerciaux compte et filtre : un « gagné » deviné fausserait les comptages ; garder le document laisse Damien corriger la source |
